# Metodo operativo

## Fundamento metodológico

Aether debe combinar descubrimiento progresivo, decisiones por criterios, planificación proporcional y aprendizaje basado en evidencia. El método comparte un núcleo estable entre contextos, pero permite que cada workspace adapte términos, plantillas y exigencias.

El principio es exigir la información necesaria para la siguiente decisión. Solicitar un Gantt completo al recibir una idea añade precisión aparente; permitir ejecutar indefinidamente sin responsable ni criterio de aceptación elimina responsabilidad.

## Unidades metodológicas

| Unidad | Pregunta que resuelve | Resultado |
| :--- | :--- | :--- |
| Necesidad | ¿Qué ocurre y a quién afecta? | Problema contextualizado |
| Hipótesis | ¿Qué cambio podría producir valor? | Supuesto contrastable |
| Iniciativa | ¿Merece evaluación y recursos? | Expediente de decisión |
| Proyecto | ¿Qué compromiso vamos a ejecutar? | Alcance y responsables |
| Entregable | ¿Qué resultado concreto se aceptará? | Producto o evidencia validable |
| Tarea | ¿Qué acción permite producirlo? | Trabajo verificable |
| Hito | ¿En qué momento evaluamos un compromiso? | Control de avance |
| Evidencia | ¿En qué se basa la conclusión? | Fuente y versión identificables |
| Decisión | ¿Qué se autorizó y por qué? | Registro atribuible |
| Aprendizaje | ¿Qué cambió en nuestra comprensión? | Mejora reutilizable |

## Etapas y puertas de decisión

Una etapa organiza trabajo. Una puerta de decisión valida que se cumplen condiciones para avanzar. Completar un formulario no equivale a aprobar un proyecto, y aprobar una iniciativa no equivale a demostrar que existe capacidad para ejecutarla.

El motor de reglas devuelve condiciones cumplidas, condiciones pendientes y acciones habilitadas. La persona autorizada decide. En contextos personales una misma persona puede cumplir varios roles, pero la aplicación debe conservar el significado de cada acción.

## Ritmo de gestión propuesto

| Ritmo | Participantes | Propósito | Registro mínimo |
| :--- | :--- | :--- | :--- |
| Continuo | Colaboradores | Actualizar compromisos y bloqueos | Estado, responsable y evidencia |
| Semanal | Líder y equipo | Revisar plan y capacidad | Próximo hito y acuerdos |
| Según vencimiento | Coordinador | Resolver ingreso y pendientes | Decisión y próxima revisión |
| Por hito | Mentor y aprobador | Validar avance y riesgos | Evidencia y resultado de revisión |
| Mensual, ajustable | Dirección | Revisar cartera y recursos | Priorización y reasignaciones |
| Al cierre | Equipo y beneficiario | Aceptar resultados y aprender | Acta de cierre y seguimiento |

Los intervalos son valores iniciales a validar en el piloto. Deben configurarse sin modificar código y respetar calendario laboral cuando el servicio se mida en días hábiles.

## Proporcionalidad

Un proyecto personal puede cumplir el estándar con un responsable, una descripción, un siguiente paso y una evidencia sencilla. Un proyecto institucional puede requerir diagnóstico, evaluación independiente, compromiso de recursos y aprobación de cierre. La simplificación reduce requisitos aplicables, pero no elimina trazabilidad ni seguridad.

Kanban es adecuado para flujo continuo. Los sprints son una opción para trabajo iterativo. El cronograma sirve cuando existen compromisos temporales. Estas modalidades comparten tareas y entregables; no deben crear copias divergentes del mismo trabajo.

## Gestión del cambio

Modificar alcance, responsable, fechas comprometidas o estándar después de aprobar exige registrar impacto y autoridad. Cambios menores pueden resolverse por el líder; cambios que alteran el objetivo o los recursos aprobados requieren una nueva revisión. Los umbrales se definen en el estándar del workspace.

El método debe permitir volver a una etapa anterior con causa explícita. El aprendizaje legítimo no es un error del sistema. La trazabilidad evita que retroceder borre decisiones previas.
