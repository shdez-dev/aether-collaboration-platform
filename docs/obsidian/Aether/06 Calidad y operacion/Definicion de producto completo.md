# Definicion de producto completo

## Definición operativa

Aether se considera completo para un alcance comercial declarado cuando cada actor puede finalizar su trabajo, los datos preservan significado y autoridad, y el servicio puede operarse y recuperarse sin reparaciones manuales habituales.

La siguiente lista es una puerta de producto. El estado inicial de verificación de todos sus puntos es pendiente en esta revisión. No se hereda aprobación de builds o sesiones anteriores.

| Puerta | Condición de salida | Evidencia |
| :--- | :--- | :--- |
| PC-01 Identidad | Alta, verificación, recuperación y revocación funcionan | Recorrido con cuentas de prueba |
| PC-02 Gobierno | Organización y workspace tienen responsabilidades transferibles | Baja y transferencia ensayadas |
| PC-03 Ingreso | Solicitante recibe respuesta y puede corregir | Expediente completo |
| PC-04 Evaluación | Criterios, versiones y autoridad son trazables | Evaluación y decisión recuperables |
| PC-05 Conversión | Un único proyecto conserva origen y roles correctos | Prueba repetida y concurrente |
| PC-06 Formalización | Cumplimiento y decisión son diferentes | Bloqueo de proyecto incompleto |
| PC-07 Ejecución | Equipo coordina tareas, hitos y dependencias | Recorrido multiusuario |
| PC-08 Evidencia | Versiones aprobadas conservan vínculo y permisos | Exportación y restauración |
| PC-09 Cierre | Se acepta resultado y se transfiere continuidad | Acta completa |
| PC-10 Visibilidad | Métricas y alertas tienen fundamento | Reconciliación contra datos de prueba |
| PC-11 Aislamiento | No hay accesos cruzados por canales alternativos | Matriz negativa completa |
| PC-12 Durabilidad | Fallos no pierden decisiones confirmadas | Ensayos de caída y reintento |
| PC-13 Operación | Instalación, migración y recuperación son reproducibles | Simulacro y runbook |
| PC-14 Usabilidad | Usuarios de cada rol completan tareas críticas | Piloto observado |
| PC-15 Soporte | Incidencias tienen diagnóstico y responsable | Procedimiento aplicado |
| PC-16 Comercial | Planes publicados cumplen contratación y límites | Flujo de pago o contratación asistida definida |

## Criterios adicionales por alcance

Para ofrecer institucional, son obligatorios ingreso, evaluación, estándares y seguimiento por responsables. Para ofrecer portfolio, son obligatorias capacidad, alertas y reportes autorizados. Para ofrecer redes, son obligatorias concesiones externas, vigencia y evaluación sin filtraciones. Para ofrecer IA, se exige revisión de propuestas, control de consumo y tratamiento de fallos.

Un módulo incompleto puede permanecer fuera de la oferta mediante una capacidad deshabilitada y una comunicación clara. Un botón visible que termina en una intervención manual desconocida no es un recorrido completo.

## Decisión de lanzamiento

El responsable de producto reúne evidencia, ingeniería verifica integridad y operación confirma continuidad. El cliente piloto valida que el flujo responde a su necesidad. Cada excepción registra impacto, responsable y fecha; ninguna excepción debe aceptar pérdida de decisiones confirmadas o acceso no autorizado.

Las metas numéricas de adopción y calidad se acuerdan antes del piloto. No se inventa una tasa de éxito ni se declara madurez sin observación.

## Mantenimiento posterior

El producto completo no es una condición permanente. Cambiar permisos, estándar, proveedor o flujo obliga a reevaluar las puertas afectadas. Cada versión publicada conserva su evidencia de liberación y sus limitaciones conocidas.
